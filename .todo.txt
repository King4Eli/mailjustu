## Needs a real, owned domain + DNS (can't be completed against the
## mail.example.com placeholder, not a code problem)
- DKIM signing works end to end (Mode "sv", confirmed by sending real
  mail and checking the delivered DKIM-Signature header) but the
  <selector>._domainkey.<domain> TXT record can't be published -- see
  ./volumes/opendkim/keys/mail.txt for the record content once you have
  a real domain.
- MAIL_HOSTNAME/MAIL_PUBLIC_IP in ./.env/api.env are still placeholders,
  so the admin dashboard's generated MX/A/SPF/DMARC records are
  structurally correct but point nowhere.
- TLS certs under ./volumes/certs and ./volumes/dovecot/ssl are whatever
  self-signed cert shipped in the base images. Replace with real certs
  (Let's Encrypt or otherwise), then tighten Postfix's
  smtp_tls_security_level from `may` (opportunistic -- sends cleartext if
  the far end doesn't support TLS) to `encrypt`.

## NEEDS ATTENTION -- real gaps, but the fix requires a decision only you
## can make (architecture/tradeoff), not just more code
- Mail queue visibility (Postfix queue depth) still isn't built. Same two
  options as before: mount the Docker socket into api/ (root-equivalent
  host access) or add a small authenticated TCP helper inside a custom
  postfix image -- this session wired the equivalent pattern for Dovecot
  (doveadm HTTP API, see api/src/doveadm.js) and ClamAV (clamav-milter,
  see docker-compose.clamav.yml), but boky/postfix is used as a stock
  image with no custom Dockerfile, so doing the same for the queue means
  taking on that build for the first time. Pick an option before building it.
- Mail activity / security event feed: still needs a log aggregation
  strategy -- Postfix logs to syslog inside its own container, nothing
  currently ships those logs anywhere api/ can read them.
- Session storage is an in-memory token map in api/ (single replica,
  wiped on restart). Redis is already running when the rspamd overlay is
  included and could back sessions instead, but that would make login
  persistence depend on an otherwise-optional add-on -- decide whether
  Redis (or MySQL-backed sessions) becomes a required part of the base
  stack, rather than silently coupling auth to an optional service.

## Cleanup / consistency, not urgent
- ./volumes/postfix/mysql-virtual-*.cf and
  ./volumes/dovecot/conf.d/auth-sql.conf hardcode the global_mysql
  credentials (mysql: map files don't support env expansion) -- if you
  rotate mail_justu_password1, update both places plus ./.env/api.env.
- The 1024M fallback quota is hardcoded in both
  ./volumes/dovecot/conf.d/auth-sql.conf's query and quota.conf, and
  mirrored in ./.env/api.env's DEFAULT_MAILBOX_QUOTA_MB purely for the
  admin dashboard's display -- same "duplicated because config can't read
  env" situation as the DB credentials above. Keep all three in sync.
- shared-global-network is `external: true` -- this compose file will
  refuse to start on a machine that doesn't already have that network
  created by whatever else manages it. Not portable as-is.
- api/test/ covers pure validation logic and the session/auth middleware
  (9 tests, `npm test` in api/) -- a real starting point, but there's
  still no coverage for the IMAP/SMTP/MySQL-backed routes themselves
  (would need a mocked or containerized integration harness). Expand
  as those routes change, don't treat 9 passing tests as "tested."

## Known limitations, probably fine to leave
- No password reset / account self-service flow -- mailbox creation is
  admin-only via the dashboard or POST /api/admin/mailboxes.
- Aliases only forward to a mailbox on this server and are locked to the
  owning mailbox's own domain -- intentional, not a bug (see README).
- MAX_MAILBOXES_PER_DOMAIN / MAX_ALIASES_PER_MAILBOX / MAX_FOLDERS_PER_MAILBOX
  / quota_mb are only checked when creating a new mailbox/alias/folder --
  lowering a limit doesn't retroactively remove anything already over it
  (storage quota is the exception: Dovecot enforces that live).
- File uploads: no size/type restriction beyond multer's 25 MB-per-file/
  10-files caps, no per-mailbox aggregate attachment quota beyond overall
  storage quota. Downloading received attachments now works
  (GET /api/mail/messages/:uid/attachments/:index).
- ClamAV milter (./volumes/clamav-milter/clamav-milter.conf) fails open
  (`OnFail Accept`) if clamd is unreachable/erroring, so a scanner outage
  doesn't block all mail -- flip to a fail-closed action there if you'd
  rather block mail than risk missing a scan.
- Rspamd's {= env.X =} config templating only resolves a handful of names
  baked into its own default rspamd.conf; custom env vars silently fall
  back to defaults instead of erroring. See the comment in
  ./volumes/rspamd/local.d/worker-controller.inc. Hardcoded there instead.
